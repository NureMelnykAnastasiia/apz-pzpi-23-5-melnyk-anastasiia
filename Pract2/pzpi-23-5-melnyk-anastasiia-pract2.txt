     3 ОПИС ВИКОНАНОЇ РОБОТИ
     Історія WhatsApp почалася у 2009 році як простого додатка для відображення статусів контактів, який завдяки впровадженню push-сповіщень швидко еволюціонував у повноцінний месенджер. За понад десять років система масштабувалася для обслуговування мільярдів активних користувачів щодня, зберігаючи при цьому команду розробників відносно невеликою. Сучасний WhatsApp – це високонавантажена система реального часу, розрахована на обробку десятків мільйонів одночасних підключень на кожному сервері. Головним викликом платформи є підтримка стабільних довготривалих TCP-з’єднань з мінімальними затримками (low latency) та забезпечення надійної доставки повідомлень (at-least-once delivery) у децентралізованому середовищі. Для вирішення цього завдання було обрано модель акторів та глибоко оптимізовано мережевий стек операційної системи. 
     Назва інструменту та версія: Gemini 1.5 Pro. 
     Мета використання: з'ясувати роль моделі акторів у платформі Erlang/OTP та значення оптимізації ОС для стабільності кодової бази WhatsApp.
      Запит (Prompt): "Explain the technical role of the actor model in Erlang/OTP and the specific advantages of using customized FreeBSD for maintaining stability in a large-scale architecture like WhatsApp's." 
     Внесок автора: проаналізовано переваги ізоляції процесів (мікропроцесів) для кожного користувача, виокремлено ключові аспекти гарячої заміни коду (hot code swapping) без зупинки серверів.
     Основним архітектурним стилем WhatsApp є використання моделі акторів на базі мови Erlang. Замість традиційних мікросервісів або моноліту система складається з мільйонів ізольованих "легковагових" процесів всередині віртуальної машини BEAM. Додатково застосовуються такі патерни:
     • AP-орієнтація (CAP-теорема): у компонентах реального часу пріоритет надається доступності та стійкості до розділення мережі;
     • Store-and-forward (Збережи та передай): сервери зберігають повідомлення в оперативній пам'яті лише до моменту їх доставки адресату;
     • Decentralized State Architecture: стан системи та криптографічні ключі зберігаються безпосередньо на клієнтських пристроях, а не в централізованій базі даних.
     Назва інструменту та версія: Gemini 1.5 Pro. 
     Мета використання: отримати опис топології серверів RTM (Ejabberd) та принципу роботи Mnesia. 
     Запит (Prompt): "Describe the server topology for WhatsApp's messaging system, focusing on customized Ejabberd servers. Also, explain how Mnesia is used for temporary message queuing and session management." 
     Внесок автора: систематизовано архітектуру обміну даними, описано механізм використання оперативної пам'яті бази даних Mnesia для швидкої маршрутизації. 
     Архітектура системи розділена на такі блоки:
     • Business Tier: рівень інтеграції для WhatsApp Business API, що забезпечує взаємодію з хмарними сервісами Meta для Enterprise-клієнтів.
     • RTM (Real-Time Messaging) Tier: Кастомізовані сервери Ejabberd, які тримають TCP/WebSocket-з'єднання. Вони використовують модифікований бінарний протокол XMPP (FunXMPP) для мінімізації трафіку.
     • Storage (Mnesia/Haystack): Розподілена база даних Mnesia працює в оперативній пам'яті (RAM) для зберігання станів сесій та тимчасових черг повідомлень. Для постійного зберігання медіафайлів використовується об'єктне сховище Meta (Everstore/Haystack) та CDN.
     • Encryption Module: Інфраструктура наскрізного шифрування (Signal Protocol), що забезпечує транзит зашифрованих пакетів без доступу серверів до їх вмісту.
     Взаємодія підсистем базується на системі підтверджень (Acknowledge). При відправці повідомлення клієнт передає зашифрований пакет на сервер Ejabberd. Подія тимчасово фіксується в Mnesia (Server ACK - перша "галочка"). Далі сервер локалізує процес отримувача. Якщо адресат онлайн, повідомлення проштовхується на його пристрій. Тільки після отримання підтвердження від клієнта-отримувача (Client ACK - друга "галочка"), повідомлення безповоротно видаляється з черги сервера. Це гарантує, що жодне повідомлення не загубиться при обриві з'єднання. Перехід до багатопристроєвої (Multi-Device) архітектури ускладнив цей процес, вимагаючи встановлення окремих сесій шифрування для кожного пристрою користувача.

Рисунок 1 – Діаграма послідовності
     Наведена діаграма на рисунку 1 демонструє повний цикл життя повідомлення – від ініціації відправником до отримання адресатом. Весь процес поділяється на дві фази: тимчасове збереження та доставка. Фаза тимчасового збереження: Користувач А надсилає повідомлення через TCP-з'єднання (FunXMPP). Система на базі Erlang/Ejabberd виконує запис у розподілену базу даних Mnesia. Після успішного запису клієнт отримує Server ACK. Фаза доставки: Сервер виступає в ролі маршрутизатора. Він перевіряє стан отримувача (Користувач Б). Якщо отримувач в мережі, повідомлення доставляється миттєво. Завершення: Користувач Б завантажує дані та відправляє системі Client ACK. Сервер Ejabberd приймає підтвердження, пересилає його Користувачу А та видаляє запис із Mnesia, звільняючи оперативну пам'ять.


4 ВИСНОВКИ
     Архітектура WhatsApp є прикладом успішної оптимізації вузькоспеціалізованих технологій (Erlang/OTP, FreeBSD) для досягнення максимальної пропускної здатності. Ключовим викликом стала необхідність управління мільйонами з'єднань на одному сервері, що було вирішено через відмову від серверного зберігання історії на користь підходу "store-and-forward". Аналіз підтвердив, що поєднання легкої моделі акторів із надійною системою підтверджень забезпечує стабільність навіть при нестабільному мобільному інтернеті. З впровадженням WhatsApp Cloud API та Multi-Device підтримки, система успішно адаптувала своє децентралізоване ядро до потреб сучасного бізнесу.
